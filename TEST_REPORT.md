## 2. Методология и ограничения среды (читать обязательно)

В данной среде **отсутствует shell-доступ**, поэтому выполнить можно только `npm run build`
(через инструмент сборки). **Невозможно исполнить:** `vitest` (прогон тестов + coverage),
`eslint`, `prettier --check`, `tsc --noEmit` как отдельную команду, Playwright/E2E, dev-консоль.

Что сделано для компенсации:
- **Типизация** верифицирована реальной TS-диагностикой, которую возвращает каждый `create_file`/
  `edit_file` (все файлы — без ошибок), плюс целевые grep-проверки (`any`, `as never`, `@ts-ignore`).
- **Логика юнит-тестов** верифицирована **статически** (ручная сверка ожиданий с доменной логикой).
  Тесты написаны и типизируются, но **не исполнялись** — это главное ограничение отчёта.
- **Функциональные сценарии (Часть 3)** проверены **статически по коду**, не в браузере.

## 8. Оставшиеся риски и рекомендации

1. **Тесты не исполнялись в этой среде.** Перед релизом прогнать `npx vitest run` и
   `vitest --coverage` в CI; ожидается зелёный прогон (логика сверена статически).
2. **Бандл 817 кБ (>500 кБ, предупреждение сборки).** Основная тяжесть — `recharts`.
   Рекомендация: code-split (`React.lazy`) вкладки «Месяц»/Insights и ленивая загрузка recharts.
3. **PDF-экспорт — print-based (HTML → «Сохранить как PDF»)**, а не jsPDF: осознанное решение для
   гарантированной кириллицы и эмодзи без встраивания TTF. Требует пользовательского шага «Печать».
4. **Привычки в корреляциях** считаются по *запланированным* дням (выполнение не трекается) — честно
   отражено в подписи `signalLabel`; полноценный учёт появится с BioSync (Этап 3).
5. **E2E (Часть 3, браузерные сценарии)** не прогонялись — нет Playwright/браузера в среде.
   Рекомендация: настроить Playwright на 3–5 критичных потоков (чек-ин, экспорт, deep link).
6. **Демо-синхронизация Google Calendar** — провайдер-заглушка; реальная двусторонняя синхронизация
   требует OAuth + Calendar API (отмечено в контракте `CalendarProvider`).
